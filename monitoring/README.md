# Vigil monitoring

The optional [values](values.yaml) pin the deployment workflow to `kube-prometheus-stack` 92.7.0 with small resource requests, private services and six-hour/500 MB ephemeral Prometheus retention. The [dashboard](vigil-dashboard.json) reads real counters and a latency histogram exported by the API/worker, plus Kubernetes replica and memory metrics. It is not populated with sample dashboard telemetry.

Run `bash scripts/deploy-monitoring.sh` from the repository root on an already deployed cluster with sufficient memory. The script generates a Grafana administrator secret, installs the stack, imports the dashboard and enables the app's ServiceMonitor/rules. No notification receiver is configured. [Operations and verification](../docs/OPERATIONS.md#monitoring-verification-and-private-access), [local validation evidence](../infra/validation.txt).

Live collection and the eight-panel Grafana dashboard were verified again on **16 October 2026** using temporary 4 GiB capacity. Prometheus reported all three application targets **UP** (two APIs and the singleton worker); Grafana showed two healthy API targets, actual request activity and a populated latency series. The [fresh dashboard capture](../demo/evidence/grafana-live.png), [Prometheus targets](../demo/evidence/prometheus-targets.png) and [query evidence](../demo/evidence/monitoring-live.json) document the result. The release, namespace, temporary viewer, private tunnels and empty owned CRDs were then removed to preserve credits and memory. Continuous Prometheus/Grafana operation is not claimed. The app still exports internal metrics and Kubernetes Metrics Server supports its HPA.

The new live capture verifies the corrected **512 MiB** Grafana limit, a 0–1 error-ratio range displayed as 0–100%, and a numeric checks-per-minute unit. It supersedes the older 15 October screenshot with incorrect axis formatting. Use at least 4 GiB host memory for the bounded review; source requests and limits do not make full monitoring suitable for the 2 GiB production host.

For a temporary video recording on a dedicated 4 GiB host, use `VIGIL_TEMPORARY_REVIEW=1 bash scripts/deploy-monitoring.sh`. This adds the [private Viewer profile](review-values.yaml), rejects unowned existing namespaces/monitoring CRDs instead of adopting them (owned reviews remain repeatable), and marks the created resources for bounded cleanup. Access only through loopback/SSM; no public ingress or admin access is enabled. After recording, run `VIGIL_TEMPORARY_REVIEW=1 bash scripts/deploy-monitoring-cleanup.sh`, close tunnels, then return to the budget host after verifying production. The regular installer keeps authentication enabled.
